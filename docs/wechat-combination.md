# Pero + webot 微信组合

目标：每次组合启动自动扫描全部微信群，完成双方连接、路由和发送范围配置。**不启动微信客户端，不代替手动登录。**

## 准备与启动

1. 更新两个仓库，按各自 README 安装虚拟环境依赖。
2. 在 Pero/frontend 执行 npm ci、npm run build。
3. 手动打开微信并登录。必要时填写 webot/bridge/config.json 的 wechat.db_dir。
4. 正常停止已有单独运行的 Core／Manager／桥。启动器不会接管它们或终止占用端口的其它进程。

并列目录时，在 Pero 运行 start-wechat.cmd；指定其它位置可使用：

```powershell
.\start-wechat.cmd --webot-root "D:\你的目录\webot" --no-browser
```

默认使用 config/local.json，支持 --config、--manager-port、--state-dir 等启动器参数。新群绑定配置中的首个 Agent；--agent-id 可指定已有 Agent，原有群绑定不批量改变。

## 自动配置

| 内容 | 行为 |
| --- | --- |
| 微信扫描 | 桥环境的 scan_groups.py 只读当前账号与所有群，不访问模型、不发送消息、不启动微信 |
| 桥群范围 | 用完整扫描结果生成 wechat.groups，清空群筛选白名单 |
| 群 ID | 按桥的 crc32 映射生成数字群目标，发现冲突即失败 |
| 路由及范围 | 新群自动加入路由、允许会话和发送目标，账号加入发送账号；保留其它账号及私聊路由 |
| 自动回应 | 开启全局自动处理与发送；各群仍经唤醒及参与策略 |
| 地址 | 对齐本机 WS、Core 内部私聊接口和账号 |
| 令牌 | Core／Manager／桥共享内部管理访问码；OneBot 使用独立用户级加密令牌，经环境注入 |
| 显示 | 控制室使用生成的 scope-labels.json 显示群名 |
| 顺序 | 扫描配置 → Core／Manager → 确认保存设置应用 → 桥 → 检查连接 |

组合入口无需逐群手工填写 JSON，但不会添加模型 Key、人格、知识资料或插件镜像，也不扩大主人跨群读取范围。

## 关闭与重扫

在 Agent → 群聊与私聊，选择群的“唤醒与 @ 设置”，关闭“启用本群接入”并保存。Core 随后拒绝正常处理本群输入或发送新回复，后台回报也重查该开关；已交给桥执行的发送不能撤回。

关闭值存于版本化会话配置，重扫不会覆盖。桥仍可能读取和上报该群，但 Core 不再接纳正常处理；这不是让微信数据库中该群完全不可见。需要桥侧不读时使用独立部署及显式群范围。

每次**重新启动组合**扫描一次，运行中不持续发现新群。先 stop.cmd 再 start-wechat.cmd；重复点击 start 只提示／打开当前实例，不热切换参数。已在运行配置手工移除的已管理群允许会话／发送目标也不会因重扫自动恢复。

账号 wxid 与首次绑定不一致、扫描失败、空结果、缺合法群名或 ID 冲突时拒绝同步，保留现有群配置。需要换机器人账号应使用独立部署并规划数据迁移。暂时未发现的既有路由保留，桥本次只监听本次扫描结果。

## 数据与停止

修改前备份到 data/launcher/backups。备份可能含原有本机凭据，属于运行数据，不提交仓库。默认还生成 wechat-groups.json、scope-labels.json、onebot-token.dpapi；这些文件都在 data/launcher 下，不包含公开提交。

连接令牌明文不写新 bridge/config.json。独立手动运行桥时需自行提供 astrbot.token_env 指定的值，或按手动部署重新规划认证；不要通过日志或 Git 传递令牌。

stop.cmd 等待对话和后台任务收尾后，停止本次桥、Core 与 Manager。微信不被关闭。保留启动窗口，直接关窗口属于中断清理。

先看控制室桥已连接、群名正确，再配置模型并在测试群用唤醒词确认回复。没填 Key 也能完成启动和路由配置，但不能得到模型回答。

实现验证采用模拟扫描及模拟桥，运行真实 Core／Manager，覆盖组合启动、认证、全群路由、群关闭持久化和重扫增量。没有代用户启动微信或发送真实消息；实际客户端兼容性需在已登录环境验证。
